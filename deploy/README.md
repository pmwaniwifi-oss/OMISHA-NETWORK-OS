# OMISHA platform integration baseline

Database separation rules and scale tradeoffs: [database isolation](database-isolation.md).

## Git-managed sources

`upstream/` contains four Git submodules at reviewed commits, recorded in
`upstreams.lock.json`: Frappe, ERPNext, Frappe Docker and NMS Prime Community.
GitHub displays these as links to the complete upstream trees. To obtain source
locally, use `git submodule update --init` after cloning this repository. This
fetches source; it does not install dependencies or run scripts. Never use
`git submodule update --remote` for a release: update pins in a reviewed PR.
Submodule source commits do not prove the provenance of a prebuilt ERPNext image.
Resolve image digests, embedded app versions and SBOM before promoting a release.

## Frappe/ERPNext laptop VM pilot

Five unchanged Frappe Docker files are vendored under `frappe/upstream/` with the
MIT license and a SHA-256 manifest, from commit
`adb65c3e6bea083095bb88dc45f589ab37ead072`. OMISHA overrides are separate.
The chosen upstream image reference is `frappe/erpnext:v16.54.0`; upstream uses
MariaDB 11.8 and Redis 8.6. Do not substitute Valkey in Frappe queues without a
compatibility test. OMISHA's separate gateway cache continues to use Valkey.

Topology: configurator, backend, frontend, websocket, two queues, scheduler,
MariaDB, Redis cache and durable Redis queue volume. Frontend binds localhost
only; no database or Redis ports are published. DB password is read from a
private mounted secret file. MariaDB automatic upgrade is disabled by overlay.

Create a private environment file from `frappe/pilot.env.example`, set an absolute
secret-file path, and use a distinct `OMISHA_STACK`, site name and localhost port
per client. No actual credentials are supplied or generated by this repository.
The wrapper defaults to validation only:

```bash
export OMISHA_ENV_FILE=/absolute/private/client1.env
export OMISHA_STACK=omisha-client1
bash deploy/frappe/compose.sh config --quiet
```

When an operator later deploys, `bash deploy/frappe/compose.sh up -d` starts the
stack. This change does not execute that command. A started stack is not a
configured ERP site: create a site using `bench new-site` interactively through
`compose.sh exec backend`, then install ERPNext on that site. Use private prompts
for passwords, not command-line arguments, logs or GitHub Actions secrets passed
to an untrusted pull request. Validate the exact pinned Bench options first.

Each pilot client gets a separate Compose project, sites/db/queue volumes and
integration credentials. This is process/network separation on one host, not VM
isolation; a host administrator can access all clients. Cloud customers requiring
stronger boundaries need separate VMs and network policy. The fixed site header
selects the configured site; it is not authentication. Remote access requires an
authenticated TLS edge and firewall plan before changing localhost bindings.

Production gates: site provisioning and login, compatible HRMS/CRM/Helpdesk and
India Compliance versions, tax/account configuration, tested backup/restore,
private signing keys, telemetry, resource limits and disk sizing. These apps are
not included in the stock ERPNext image just because they appear in the plan.
Never `down --volumes` on a real deployment. Upgrades require a restored staging
copy, pre-migration backup and tested restore rollback; rolling back an image
does not reverse a database migration.

## NMS Prime integration boundary

Pinned Community source: `cablelabs/os-provisioning` at
`117cf48e917681c6c47ba966132c2fbf1e606f4b`. This is NMS Prime, not Cisco Prime.
The root README specifies Rocky/RHEL 9 and RPM-based installation, with
PostgreSQL, DHCP/Kea, BIND and monitoring dependencies. No Dockerfile or Compose
deployment was found in this pinned tree. A PHP web container alone would not
provide its network provisioning platform. Therefore NMS Prime remains a
separate supported Rocky Linux 9 host/VM connected by HTTPS to the OMISHA adapter.
All source and integration configuration remain Git-managed; deployment is not
performed in this change. Do not run the legacy carrier installer or upstream
bootstrap scripts in CI. Enterprise modules require separate entitlement review.

Read-only Go adapters now implement:

| Source | Request | Credential | Source evidence |
|---|---|---|---|
| ERPNext | `GET /api/resource/Customer/{name}` | per-site API key/secret | Frappe REST documentation |
| NMS Prime | `GET /admin/api/v0/Contract/{id}` | limited Basic-auth API account over TLS | `app/extensions/core/BaseRoute.php`, `modules/ProvBase/Http/routes.php`, `AuthenticateNmsPrimeApi.php` |

Adapters require a fixed tenant and HTTPS origin, reject redirects, bound body
size and duration, honor cancellation and validate response envelopes. They
remain internal Go library code; `/v1/` remains 501 until authenticated routing
and customer-to-record authorization exist. Mock TLS contract tests do not prove
the credentials, permissions or response shape on an actual installed NMS/ERP.
Create a dedicated NMS account with the required `use api` and read permissions.
Never infer that every GET is safe: NMS exposes device-changing GET actions.
The adapter deliberately cannot call arbitrary paths or provisioning actions.

No direct NMS or ERP database writes. Next: tenant identity registry, authenticated
BFF ownership checks, confirmed API contracts, transactional service-order outbox,
idempotent provisioning, and invoice reconciliation. GST remains ERPNext's ledger
workflow; network events never fabricate statutory ledger entries.

## Public repository and licenses

Source visibility does not make customer data, signatures or service credentials
public. Keep those under private runtime storage; never add a real `.env`, backup,
mailbox attachment or site configuration. Submodules preserve upstream licenses:
Frappe and Frappe Docker MIT; ERPNext GPLv3; NMS root LICENSE Apache-2.0. NMS's
Composer metadata also says MIT; do not use that field to relicense the entire
project. Audit included module/dependency notices separately. OMISHA still has no
root LICENSE decision; public GitHub visibility is not a commercial license grant.
OMISHA paid support/entitlements must respect upstream distribution/source rights.

## Evidence and remaining acceptance

`scripts/verify_upstreams.py` verifies Git links and vendored checksums without
executing upstream code. CI validates rendered Compose topology and registry
availability of image tags; it does not deploy Frappe/NMS. Go tests cover TLS
requests, tenant mismatch, redirects, malformed/oversized data and cancellation.
Full product acceptance still needs real NMS/ERP sandbox, selected PM-WANI role
and API, operator-approved report templates, mailbox authorization, authenticated
roles/seat enforcement, mobile releases and signed backups/restore drills.
